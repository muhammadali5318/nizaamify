## Decision 1 — `reverse_ledger_entry`: retire the key, or keep it as a base gate?

### 1.1 What 0103 already did

`0103_v210_modify_existing_rpcs.sql` rewrote `reverse_ledger_entry`
(lines 1048–1141) implementing the C2 *pure direction-split*: the
function fetches+locks the entry, then gates on `receive_payment` (if
`direction='receivable'`) or `pay_supplier` (if `direction='payable'`).
**It no longer references the `reverse_ledger_entry` permission key at
all.** As of 0103 applied to staging, the catalog key is **orphaned** —
present in `permissions_catalog`, present in production's
`user_shop_permissions` (manager ✓ / salesperson ✗), referenced by
nothing.

Evidence (staging function-body scan): no surviving `public` function
references `'reverse_ledger_entry'`.

### 1.2 The two consequences the implementation plan flagged (§1.4)

**(a) Salesperson escalation.** In the v2.10 catalog the salesperson
preset holds `receive_payment` (✓). With the pure direction-split, that
*alone* lets a salesperson reverse **receivable** ledger entries. The
dedicated v2.9 `reverse_ledger_entry` key never granted them that
(salesperson ✗). Retiring the key accepts the widening ("if you can take
payments, you can correct them"); a base gate checked first closes it.

**(b) `entry_not_in_shop` disclosure.** The direction-split forces the
permission check *after* the entry fetch (direction is unknown until the
row is read). So a caller holding **neither** `receive_payment` nor
`pay_supplier` who probes `reverse_ledger_entry(<uuid>)` learns, from the
error code alone, whether that UUID is a ledger entry in their active
shop: `insufficient_permissions` (it is) vs `entry_not_in_shop` (it
isn't). A salesperson by default holds neither `view_contact_customer_data`
nor `view_contact_supplier_data`, so they cannot otherwise enumerate
ledger rows — this probe is a (low-severity, UUID-guessing) read-side
channel they would not otherwise have. A base gate checked *before* the
fetch restores authz-before-fetch ordering and removes the channel.

### 1.3 Options

| | **A — Retire** | **B — Keep as base gate** *(recommended)* |
|---|---|---|
| Catalog | `DROP` the key | Keep; rebind `requires` `[view_customer_khata]` → `[view_contacts]` (the v2.9 dependency key is itself dropped); preset stays O✓ M✓ S✗ |
| `user_shop_permissions` | drop its 2 production rows | keep its 2 production rows unchanged (already preset-consistent: mgr ✓, sales ✗) |
| Function | no change (0103 already removed the reference) | `CREATE OR REPLACE reverse_ledger_entry` to add an up-front `user_has_permission(shop,'reverse_ledger_entry')` gate **before** the entry fetch; the direction-split sub-gate stays as the second check |
| Salesperson escalation (a) | **accepted** | **closed** — salesperson preset stays ✗, base gate blocks them even though they hold `receive_payment` |
| `entry_not_in_shop` disclosure (b) | **accepted** | **closed** — gate precedes the fetch |
| Drop count | 12 keys dropped | 11 keys dropped |

### 1.4 Recommendation — **Option B (keep as base gate)**

Reasons:

1. **Faithfulness.** v2.9 deliberately gave ledger reversal its own key
   and withheld it from salespeople. Retiring it widens salesperson
   capability *as a side-effect of an implementation refactor* (the
   direction-split). That is precisely the move 0104b's header warned
   against — "a corrective migration corrects the defect, it does not
   smuggle in a behaviour change." The same discipline applies to a
   redesign migration: a catalog cleanup should not silently re-grant a
   capability.
2. **Authz-before-fetch.** Restoring the base gate ahead of the fetch
   removes the `entry_not_in_shop` ordering inversion. AQ-23 is a LIKE
   check and order-independent, so a base-gate-first shape still passes
   (confirmed: attack-surface §6 flag F2 already anticipates this).
3. **Cost is one `CREATE OR REPLACE` + one kept catalog row.** Cheap,
   and the rebind `requires → [view_contacts]` keeps the catalog
   coherent (see Finding A for why `[view_contacts]`, not a
   customer-side key — reversal can be payable-side too).

**Scope note.** Option B adds a function-body rewrite to a migration
otherwise scoped "catalog redesign". Two ways to land it: **(i)** fold
the `CREATE OR REPLACE` into 0105 under an explicit `§` (recommended —
it is tightly coupled to the catalog decision and 0105 is small), or
**(ii)** a `0105b` corrective (precedent: 0104b). Recommending (i).

## Decision 2 — `deactivate_tier` wrapper: explicit `assign_contact_tier` gate, or transitive-via-trigger?

### 2.1 Current behaviour (post-0104b)

- The **wrapper** `deactivate_tier(uuid)` (live def from `0080`) gates on
  `manage_customer_tiers` only, then calls `deactivate_tier_v28`.
- `deactivate_tier_v28` (rewritten by 0104b) bulk re-points members:
  `UPDATE public.contacts SET customer_tier_id = <default> WHERE shop_id = … AND customer_tier_id = p_tier_id`.
- That `UPDATE` fires `v210_contacts_tier_change_gate` →
  `check_contact_tier_change_gate()`, which **unconditionally requires
  `assign_contact_tier`** whenever `customer_tier_id` changes.

So today the requirement is **data-dependent**:

| Tier being deactivated | Permissions actually needed |
|---|---|
| has **0** members | `manage_customer_tiers` only (UPDATE matches 0 rows → trigger never fires) |
| has **≥1** member | `manage_customer_tiers` **and** `assign_contact_tier` (trigger fires per row) |

0104b's header explicitly deferred this to 0105: *"Whether
deactivate_tier's wrapper gate should ALSO require assign_contact_tier …
is a permission-model question routed to the 0105 design agenda."* It
also established the bar: v2.9's `deactivate_tier` behaved this exact way
(transitive via `v29_customers_tier_change_gate`), so changing it is a
*behaviour change* that must be justified, not a default.

### 2.2 Options

| | **A — explicit wrapper gate** | **B — leave transitive** | **C — `requires` dependency** *(recommended)* |
|---|---|---|---|
| Mechanism | add `if not user_has_permission(shop,'assign_contact_tier') then raise` to the wrapper body, up-front | no change beyond the mechanical `manage_customer_tiers`→`manage_contact_tiers` key-string swap | no function-body change beyond the key-string swap; **add `assign_contact_tier` to `manage_contact_tiers.requires`** in the catalog |
| Empty-tier deactivation by a `manage`-only holder | **blocked** (was allowed in v2.9) | allowed (faithful to v2.9) | not reachable — see below |
| Data-dependent inconsistency | removed | remains, but observable only via override | **removed** — becomes unobservable |
| Behaviour change vs v2.9 | **yes** — over-gates the empty case | none | none at runtime; tightens the *grantable* permission space only |
| Single runtime enforcement point | wrapper **and** trigger (drift risk) | trigger only | trigger only |
| Dependency is self-documenting | in the wrapper body | nowhere | **in the catalog** (`requires`) |

### 2.3 Why C

The data-dependency in B is not actually a bug — *the permission tracks
what the operation does*: deactivating an empty tier reassigns nobody, so
requiring `assign_contact_tier` for it would be over-gating (this is why
A is a real behaviour change, not a fix). The genuine problem with B is
**discoverability**: an owner who grants a manager `manage_*_tiers` but
not `assign_*_tier`, tests on an empty tier, and concludes "manager can
deactivate tiers" — then the manager hits a populated tier and is
blocked.

C fixes discoverability without the over-gating of A and without a
function-body logic change:

- `manage_contact_tiers.requires = ['assign_contact_tier']` makes the
  29-rule dependency engine **guarantee** that any holder of
  `manage_contact_tiers` also holds `assign_contact_tier`. The
  empty/populated inconsistency then *cannot be observed* — you cannot
  reach `deactivate_tier` without `manage_contact_tiers`, and you cannot
  hold that without `assign_contact_tier`.
- The **trigger stays the single runtime enforcement point** — it
  already catches *every* `customer_tier_id` re-point path, not just
  `deactivate_tier`. An explicit wrapper gate (A) is redundant
  belt-and-suspenders that can drift from the trigger.
- **Faithful.** It changes no runtime behaviour for any caller who could
  already invoke `deactivate_tier`: by preset, `manage_*_tiers` holders
  are owners (implicit-all). The only thing C forecloses is a
  *nonsensical manual override* — `manage_contact_tiers` without
  `assign_contact_tier` — which is incoherent anyway. No preset (O/M/S)
  violates the new dependency, so seeding is unaffected.

### 2.4 Recommendation — **Option C**

Wrapper bodies get only the mechanical `manage_customer_tiers` →
`manage_contact_tiers` key-string swap (Part 2 §4 — all 4 tier
wrappers). The permission-model intent is carried by one extra entry in
the new key's `requires` array, not by a divergent gate in one of four
sibling wrappers.

## Finding A (surfaced during the live-state pull) — `receive_payment.requires` is incoherent with the locked presets

Not on the §1.4 agenda; surfaced reviewing the catalog. It is a judgment
call (so it needs a ruling), but lower-stakes than Decisions 1–2.

### A.1 The incoherence

Attack-surface §1.2 locks `receive_payment` with
`requires = [view_contacts, view_contact_customer_data]` and presets
O✓ M✓ **S✓**. But `view_contact_customer_data` has preset **S✗**.

A permission's `requires` array means "to hold this key you must also
hold every key listed." So the locked salesperson preset is
**self-contradictory**: salesperson holds `receive_payment` but not its
required `view_contact_customer_data`.

This is not hypothetical. Under Policy 2 intersect (Part 2 §3),
production's salesperson user migrates to exactly that state:
`receive_payment = true` (key kept), `view_contact_customer_data = false`
(the `view_customer_outstanding ∧ view_customer_khata` intersect *fails*
— salesperson has outstanding but not khata). 0105 would *produce* a
dependency-violating row and its own verification block (if it checks
`requires` coherence — and it should) would halt on it.

### A.2 Root cause

v2.9 `receive_payment` required `[view_customers, view_customer_outstanding]`.
`view_customers → view_contacts` maps cleanly. But
`view_customer_outstanding` does **not** map cleanly: it folds — lossily,
via intersect with `view_customer_khata` — into the *broader*
`view_contact_customer_data` (which absorbs **both** outstanding and
khata). Binding `receive_payment` to `view_contact_customer_data`
therefore (i) over-constrains it — adds a transitive *khata-detail*
requirement v2.9 `receive_payment` never had — and (ii) collides with
B.4's deliberate decision to withhold `view_contact_customer_data` from
salespeople while keeping `receive_payment` for them.

### A.3 Options

- **(a)** `receive_payment.requires = [view_contacts]` *(recommended)* —
  decouple. `receive_payment` does not *need* balance visibility to post
  a credit; whether the cashier *sees* the running balance is a
  view-projection concern (`contacts_view` already gates
  `customer_outstanding_balance` on `view_contact_customer_data`), not a
  call-gate concern. Coherent with the locked §1.2 presets; faithful (no
  stricter than v2.9 — arguably looser, which is the safe direction for
  a key salespeople already had).
- **(b)** flip salesperson `view_contact_customer_data` preset to ✓ —
  contradicts B.4 ("strict, owner-conservative") and attack-surface §1.3
  ("Salesperson loses outstanding visibility as expected").
- **(c)** flip salesperson `receive_payment` preset to ✗ — removes a
  core POS capability salespeople have today; contradicts §1.2.

### A.4 Recommendation — **(a)**: `receive_payment.requires = [view_contacts]`

Smallest change, restores catalog coherence, keeps every locked preset
intact, faithful-or-looser. It also makes the Decision 1 rebind
consistent: `reverse_ledger_entry.requires` likewise becomes
`[view_contacts]` — ledger reversal spans both directions, so a
customer-side dependency key would be wrong there too.
