## 0. Two scope corrections the locked docs do not capture

The implementation-plan §1.0 line for 0105 reads: *"Insert 12 new keys;
migrate 24 user_shop_permissions rows; drop 12 retired keys;
customers→contacts category rename + drop suppliers category."* The
live-state pull shows that under-describes the migration.

### Correction 1 — staging has **0** rows to migrate; the "24" is production-only

| | staging (0105's first target) | production (combined deploy) |
|---|---|---|
| `user_shop_access` | 1 — **owner only** | 2 non-owner users |
| `user_shop_permissions` | **0 rows** | 100 rows; **24** in 0105's scope |

The audit's "live DB query" (§5.1/§5.2 of the pre-design audit) was run
against **production**. Staging's seed is one owner
(`v210-seed-owner@staging.local`) and nothing else; owners never hold
`user_shop_permissions` rows (RBAC implicit shortcut). **On staging,
0105's row migration is a no-op over an empty set.** Consequence: the
end-of-migration verification block (attack-surface §1.3) **must not
hard-code "expect 24 rows" or "expect 2 users"** — it must derive
expected counts from the pre-migration state, or it will falsely
`RAISE EXCEPTION` and halt on staging where the correct answer is 0.
See §5.

The Policy 2 logic still has to be *written correctly* (§3) — it runs
for real at the combined production deploy, and against any staging
environment later seeded with non-owner members — it just migrates
nothing on staging today.

Two facts fall out:

1. **`v29_ledger_read` on the live `ledger_entries` table gates on
   `view_customer_khata` — a key 0105 drops.** Once dropped,
   `user_has_permission(shop,'view_customer_khata')` returns false for
   every non-owner → **no non-owner can read `ledger_entries`**. That
   breaks the khata UI and every contact RPC that reads the ledger.
   Attack-surface §2.2 *specifies* the replacement (`v210_ledger_read`,
   direction-aware, gating on `view_contact_customer_data` /
   `view_contact_supplier_data`) but **assigns it no migration number**,
   and migrations 0096–0104b did **not** implement it (confirmed:
   `v29_ledger_read` is still live on staging). Its natural and only safe
   home is **0105** — the new policy references keys that do not exist
   until 0105 inserts them. **0105's scope must include
   `DROP POLICY v29_ledger_read; CREATE POLICY v210_ledger_read`.**

2. **The `contacts` RLS policies, `contacts_view`, `total_outstanding`,
   and `total_payable` already reference the 12 new keys** — they were
   deployed by 0096/0102/0104 *ahead of the keys existing*. This is
   coherent, not a bug: it has "worked" on staging only because staging
   has just an owner (implicit-all bypasses `user_has_permission`
   regardless of whether the key exists). **0105 is the activation
   point** — inserting the 12 keys is what lights up every
   already-deployed consumer. This makes the *ordering inside 0105*
   load-bearing (§5): **insert keys first**, then everything else.

The `customers` / `suppliers` policies referencing dropped keys are
**inert** — those tables are frozen-dead post-0104 (AQ-33 confirms no
function writes them) and are dropped *with their policies* at 0106. No
0105 action; noted in §6 as a known inert dangler.

## 3. The 24-row migration — Policy 2 + Policy 3-B, worked through

Policy 2 (locked 2026-05-14, attack-surface §1.3): **where two old keys
fold into one new key, grant the new key only if the user held BOTH old
keys.** And — the subtlety the worked example makes concrete — for 1:1
and union maps the migrated value comes from the **legacy grant**, not
the new preset.

Policy 3-B (ruled 2026-05-14 at the 0105 file review — recorded as the
ADR's named "Policy 3"): **net-new keys with no v2.9 analog migrate to
`false`** for every existing non-owner. The B.4 preset default for those
keys seeds *new invitations* only — it is never applied retroactively to
a migrating user. Same principle as Policy 2: a migration preserves what
was demonstrably held, it never grants.

### 3.1 The mapping (attack-surface §1.3), annotated by rule

| Old key(s) | → New key | Rule |
|---|---|---|
| `view_customers` | `view_contacts` | 1:1 — copy legacy grant |
| `view_customer_contact` | `view_contact_contact_info` | 1:1 — copy legacy grant |
| `view_customer_outstanding` **∧** `view_customer_khata` | `view_contact_customer_data` | **intersect** — granted iff *both* true |
| `view_suppliers` | `view_contact_supplier_data` | 1:1 — copy legacy grant (may exceed the new M✗ preset; intended per §1.3) |
| `create_customer_basic` | `create_contact_basic` | 1:1 — copy legacy grant |
| `create_customer_full` | `create_contact_full` | 1:1 — copy legacy grant |
| `edit_customer` **∪** `manage_suppliers` | `edit_contact` | **union** — granted iff *either* true |
| `assign_customer_tier` | `assign_contact_tier` | 1:1 — copy legacy grant |
| `manage_customer_tiers` | `manage_contact_tiers` | 1:1 — copy legacy grant |

(Neither production user is in this case — User A holds both, User B
holds neither.)

### 3.5 The migration mechanism (per user, set-based)

For each existing `user_shop_permissions` row set (keyed by
`user_shop_access_id`):

1. **INSERT 12 new rows** — one per new key, `granted` computed by §3.1:
   the 9 mapped keys by intersect / union / 1:1 over the legacy rows,
   the 3 net-new keys by a `false` literal (Policy 3-B). `source =
   'preset'`, `granted_by_user_id = NULL` (schema-nullable, FK to
   `profiles` — NULL is legal), `granted_at = now()`. Expressed as a
   single `WITH legacy AS (…) INSERT … SELECT` with a 12-branch
   `UNION ALL`, *not* row-by-row procedural code.
2. **DELETE the in-scope legacy rows** — `WHERE permission_key IN (<the
   11-key drop set>)`; removes whatever subset of the 11 each access
   actually holds. Must run *after* step 1's INSERT reads them.
3. `receive_payment` / `reverse_ledger_entry` rows are **not touched** —
   only their catalog `requires` change (§1).

On staging both steps process **0 rows** (no `user_shop_permissions`).
The statements still execute — they are just empty. The verification
block (§5) is what must tolerate that.

## 5. Migration ordering and the verification block

### 5.1 Ordering inside the single `BEGIN … COMMIT`

The ordering is load-bearing (§0 Correction 2): consumers deployed since
0096 reference the new keys; nothing may reference a key being dropped.

1. **INSERT the 12 new keys** into `permissions_catalog`. *(Activates
   `contacts` RLS, `contacts_view`, `total_outstanding`,
   `total_payable`, and the 0102/0103 RPCs — all already deployed.)*
2. **Rebind dangling `requires`:** `receive_payment` → `[view_contacts]`
   (Finding A); `reverse_ledger_entry` → `[view_contacts]` *(Decision 1 =
   B)*; `record_purchase` — `array_replace(view_suppliers →
   view_contact_supplier_data)`.
3. **`CREATE OR REPLACE`** the 4 tier wrappers (§4) — swap key string.
   *(Now nothing references `manage_customer_tiers` except the catalog
   row itself.)*
4. **Swap the ledger RLS policy:** `DROP POLICY v29_ledger_read ON
   ledger_entries; CREATE POLICY v210_ledger_read …` per attack-surface
   §2.2. *(Now nothing on a live table references `view_customer_khata`.)*
5. *(Decision 1 = B)* **`CREATE OR REPLACE reverse_ledger_entry`** — add
   the up-front base gate ahead of the entry fetch (Part 1 §1.4).
6. **Migrate `user_shop_permissions`** — INSERT 12 new rows per access,
   then DELETE the old rows (§3.5). *(0 rows on staging.)*
7. **DROP the 11 (or 12) old keys** from `permissions_catalog`. *(Safe
   now: no live-table policy, no function, no view, no
   `user_shop_permissions` row references them. The `customers` /
   `suppliers` policies still do — inert, §6.)*
8. **Verification block** (§5.2) — `RAISE EXCEPTION` on any mismatch.

### 5.2 Verification block — must derive expectations, not hard-code "24"

Per §0 Correction 1, hard-coding production's counts halts the migration
falsely on staging. The block runs these checks, all derived from state:

- **Catalog totals.** `contacts` category = 11; `suppliers` category =
  0; `customers` category = 0; total keys = `<pre-count> − <drop-count>
  + 12`. Drop-count is 11 or 12 per Decision 1.
- **New keys present.** All 12 new keys exist and `is_active = true`.
- **Old keys gone.** Zero rows in `permissions_catalog` for the drop
  set.
- **`user_shop_permissions` row-count delta — derived per access, no
  shape assumption.** The §0 snapshot captures, per access, **both**
  `pre_count` **and** `legacy_in_scope_count` (how many of the 11
  in-scope legacy keys it actually holds as rows). §6 deletes exactly
  `legacy_in_scope_count` rows (the 11-key `IN`-list matches whatever
  subset exists) and inserts exactly 12, so the check asserts
  `post_count = pre_count − legacy_in_scope_count + 12`. This is correct
  whether `user_shop_permissions` is **dense** (the verified production
  shape — both non-owner accesses hold all 11; the constraint set permits
  but does not enforce density) or **sparse**. Hard-coding `+1` would
  false-halt on a sparse access — the 0104 `total_outstanding` class. On
  staging the snapshot is empty → vacuous; on dense production it
  reduces to 50 → 51 for User A and User B.
- **No orphaned `user_shop_permissions` rows.** Zero rows whose
  `permission_key` is absent from `permissions_catalog`.
- **`requires` coherence (catches Finding A regressions).** Zero
  `user_shop_permissions` rows where `granted = true` and some key in
  that key's `permissions_catalog.requires` is *not* also granted=true
  for the same access. (This is the check that would have caught the
  incoherent `receive_payment.requires`; with Finding A = (a) it passes.)
- **No live-table RLS / function / view references a dropped key.**
  Re-run the §0 scan filtered to `table_fate = 'LIVES ON'` and to
  `public` functions/views — expect 0. (`customers` / `suppliers`
  policies excluded — inert, §6.)

If any check fails → `RAISE EXCEPTION` → the `BEGIN … COMMIT` rolls back
whole. Then the down-migration (§7) is moot (nothing committed).
