# Gotchas / hard-earned lessons

Footguns and non-obvious rules learned during the build. Load this when working in the relevant area — most are still active.

## SQL / Postgres / Supabase

- **`pg_trgm` set_limit** is per-statement, not persistent — set it inside each search function via `perform extensions.set_limit(0.2)`.
- **`pg_trgm` lives in `extensions` schema** (moved in v1.8). Functions that use the `%` operator, `similarity()`, or `set_limit()` need `set search_path = public, extensions, pg_catalog`.
- **Append-only triggers block backfill UPDATEs.** When a v1.9-style migration adds a column with a default of 0 and needs to backfill existing rows from another column, you must `ALTER TABLE … DISABLE TRIGGER <name>` for the duration of the UPDATE, then re-enable. See §B of `0024_v19_suppliers_landed_cost.sql`. v2.6's 0039 migration uses the same pattern for the variant_id backfill on `sale_items` and `purchase_items`; `product_packs` has only a touch trigger so no toggle is needed there.
- **Postgres unique indexes** need `WHERE is_active = true` to allow re-using a name after archiving — used on suppliers and products.
- **RLS `auth.uid()` should always be `(select auth.uid())`** so the planner caches it per query (v1.8).
- **Supabase auto-grants EXECUTE explicitly** to `anon`, `authenticated`, and `service_role` on every newly created function — `revoke from public` alone is a no-op for anon. The pattern is: `revoke … from public, anon; grant … to authenticated;` (caught in v1.8a / v1.9a).
- **`SECURITY DEFINER` trigger functions** (e.g. `products_normalize_trigger`) needed when the trigger calls another helper that authenticated doesn't have EXECUTE on (caught in v1.8b).
- **`create or replace view`** cannot change column types. When casting a computed sum to `numeric(12,2)` you must `drop view; create view`.
- **Restoring an RPC body via migration**: `CREATE OR REPLACE FUNCTION` cannot change a function's parameter list. When v2.1 reverted `record_sale` to v1.6 shape it kept the same signature, so REPLACE worked; when v2.2 added `p_tier_override_type` / `p_tier_override_value`, the migration `DROP FUNCTION` first then created the new shape. Pattern: signature-changing rewrites need DROP + CREATE in the same transaction.

## Stock / sales / purchase RPCs

- **`record_sale` and `record_purchase` lock** product rows with `FOR UPDATE` before reading stock and avg_cost; concurrent stock-ins on the same product are race-safe.
- **`reverse_ledger_entry` blocks sale-tied debits** — entries with `invoice_id IS NOT NULL` raise `cannot_reverse_invoice_tied_debit` so callers go through `receive_payment` (or future `void_sale`) instead.
- **Landed-cost allocation** (v1.9): overhead is distributed pro-rata by line value into `purchase_items.overhead_per_unit`. `avg_cost` uses the effective unit cost (= `cost_at_purchase + overhead_per_unit`); `last_purchase_cost` stays at the supplier's quoted unit cost. Don't conflate the two.
- **Largest-remainder overhead allocation** (v2.3, replaces v1.9 per-unit method): `record_purchase` distributes overhead pro-rata by line value into `purchase_items.line_overhead_amount` (NOT `overhead_per_unit`). The CTE computes a raw share, then the leftover penny (subtotal − sum-of-rounded-shares) goes to the highest-value line. This is exact: `sum(line_overhead_amount) = overhead_subtotal` always. The legacy `overhead_per_unit` column is kept for back-compat; UI reads `line_overhead_amount` first, falls back to `overhead_per_unit × qty_in_base` on legacy rows.
- **`record_sale` / `record_purchase` accept variant_id (preferred) OR product_id (legacy → default variant)** (v2.6, ADR-0025). Items missing both raise `item_missing_variant_or_product_id`. Items passing a product_id whose product has no default variant raise `product_has_no_default_variant` (mostly a v2.7 multi-variant footgun). New code MUST pass `variant_id`.
- **Stock decrements on `product_variants.stock`, never on `products.stock`** (v2.6, ADR-0022). The `products.{stock, price, cost, avg_cost, last_purchase_cost}` columns are deprecated; reads via `product_with_default_variant` and `product_stock_display` get fresh values from the variant. Direct reads against `products.*` for stock/price post-v2.6 will silently show stale data forever.
- **Every product has at least one variant** (v2.6, ADR-0023). Single-variant products have exactly one variant with `is_default = true`; v2.7+ multi-variant products have many variants and none of them carry `is_default`. The compat view `product_with_default_variant` LEFT JOINs the default variant — for multi-variant products (post-v2.7) the variant fields are NULL there and the UI reads aggregates from a different view.
- **`sale_items.product_id` / `purchase_items.product_id` / `product_packs.product_id` are denormalized columns kept in sync by the `sync_product_id_from_variant` trigger** (v2.6, ADR-0024). Writers pass only `variant_id`; the trigger fills `product_id`. Do not write to `product_id` directly — the trigger overwrites your value on every UPDATE.
- **Pack-management RPCs (`define_pack_inline`, `update_pack`, `deactivate_pack`) still accept `p_product_id` for back-compat** (v2.6). Internally they resolve to the product's default variant and operate on `product_packs.variant_id`. v2.7 will add `p_variant_id` overloads when multi-variant packs become real.

## Discounts & money

- **Discount stacking order is fixed** (v2.2 §1, unchanged in v2.3): negotiated unit price → per-line discount → sale-discount popup → service charge added last. Discounts never touch service. Snapshots on invoice + sale_item rows mean future edits never rewrite history.
- **v2.3 partial reversion of v2.2** (ADR-0017): `customer_tiers.discount_percent` is dropped, tiers are pure categories. The invoice columns `tier_override_type/value` and `tier_discount_*` were renamed to `sale_discount_*`. Tier joins on the invoice (via `invoices.tier_id`) survive — they're a snapshot of *which tier the customer was on at sale time*, used purely for analytics/display, not discount math. The popup is the only invoice-level discount source.
- **Profit display had a Class-1 bug** (2026-05-12 P0). Two independent profit code paths — `SaleDetailPage.tsx` per-line cell and `monthly_summary.gross_profit` view (Dashboard / Reports) — both ignored the invoice-level `sale_discount_amount`; the view additionally ignored line discounts. Stage 1 (the initial commit) applied a minimum allocation-side fix in the JS cell only; **Stage 2 (v2.6c)** consolidated the canonical math behind `sale_item_financials` + `invoice_financials` so both display sites read the same number. Root cause in `decisions/2026-05-12-profit-calculation-bug-root-cause.md`; ADR for the single-source-of-truth in `decisions/2026-05-12-invoice-financials-single-source-of-truth.md`.
- **No JS Number arithmetic on money paths** (v2.6c, see `decisions/2026-05-12-no-js-number-on-money-paths.md`). Authoritative money totals must come from a SQL view (e.g. `invoice_financials`, `purchase_item_financials`, `daily_sales_7`, `expenses_by_category_mtd`, `total_outstanding`, `invoices.outstanding` generated column). JS may only cast `Number(...)` at the `formatPKR()` boundary — never to participate in `+ - * /` between money values. Display paths (post-write) MUST read from views; composition paths (POS cart, NewPurchase form preview) compute in JS because no DB row exists yet — those previews are explicitly cosmetic and the server is authoritative on submission. Migrations 0051–0056 establish the views; do not regress by computing money in a new page.
- **Receipt.tsx subtotal is a known composition-path leak** (v2.6c). The post-sale receipt computes a subtotal by `qty × price` reduce on in-memory cart lines. The displayed final `total` is server-truth (returned by `record_sale`), but the per-line breakdown above it is still JS-side. Promoting Receipt to refetch `invoice_financials` by `invoice_id` post-sale is on the open-todo list — until then, the subtotal block can disagree with `invoice_financials.items_subtotal` by penny rounding if line discounts or allocated sale discount apply.

## Packs, categories, variants

- **`product_packs` has no `price` column** (v2.0's pack-as-sellable-unit design was scrapped in v2.1). Pack pricing was determined to be overkill for SME tier. If a B2B customer ever asks for receipt-level "1 carton (50 each) @ 1,200" pricing, it's a v3 ticket — don't add a price column to packs without revisiting the v2.0 → v2.1 supersession.
- **Frontend never recomputes pack breakdown** (v2.1 §5.2). The `product_stock_display` view exposes `whole_packs` and `remainder_base` already computed; consume them directly. The original "5 cartons + 5 each" off-by-one bug came from JS recomputation drifting from DB truth — keeping one source authoritative is the fix.
- **Categories are per-shop entities, never freetext** (v2.5). `products.category_id` is the FK; `products.type` is a deprecated snapshot kept only until a future cleanup migration audits all readers. New code MUST read/write `category_id`. The unique index on `products` is `(shop_id, lower(trim(name)), category_id)` — two products may share a name across categories within a shop. ADR-0019.
- **`create_product_with_opening_stock` has a back-compat `p_type` parameter** (v2.5). New callers MUST pass `p_category_id`. The `p_type` fallback exists only so a stale tab in the field doesn't 500. It auto-creates / resolves the category from the type string. The parameter and the legacy `products.type` column drop together in a future cleanup.
- **A product can have at most 3 variant attributes** (v2.7, ADR-0027). Enforced both at the UI (the "+ Add another attribute" affordance hides at 3) and in `create_product_with_variants` (`too_many_attributes` exception). The matrix UI's 2D grid is the visual ceiling; 4+ attributes have no clean layout.
- **Variant attributes are shop-wide, not per-product** (v2.7, ADR-0026). Color / Size / Storage live in `variant_attributes (shop_id, name)`. Two products in the same shop pick from the same value pool — so "how much Red did we sell across all garments?" stays a simple join.
- **`enforce_variant_default_invariants` trigger** (v2.7, migration 0045) rejects `is_default = true` on a variant whose product has `has_variants = true`. Partial indexes can't express that invariant because Postgres rejects subqueries in WHERE predicates — the row trigger is the only way to enforce "multi-variant products may not have a default."
- **`create_product_with_variants` requires exactly one value per attribute per variant** (v2.7). The RPC raises `variant_must_have_one_value_per_attribute` if a variant's `attribute_value_ids` length doesn't match the product's `attribute_ids` length. The UI matrix builder enforces this by construction (every cell is a cross-product of selected values).

## Batches (v2.8+)

- **For batched products, `sale_items.cost_at_sale` is the BATCH's `cost_per_unit`, not the variant's `avg_cost`** (v2.8, ADR-2026-05-12-batch-cost-vs-avg-cost-on-sales). This is what makes profit per batch accurate. `invoice_financials.gross_profit` reads `cost_at_sale` directly so no view change was needed, but **anyone writing new profit math must respect this rule** — don't reach back to `variant.avg_cost` when the line carries a `batch_id`.
- **A single cart line can produce multiple sale_items rows when it spans multiple batches** (v2.8, ADR-2026-05-12-multi-batch-line-split-data-model). FEFO walks active batches ordered by `expiry_date asc nulls last, received_at asc, id asc` and consumes them in turn; one row per batch consumed. UI summarizes ("From batches X + Y") — don't assume sale_items rows are 1:1 with cart lines. `line_discount_amount` is split across rows via largest-remainder by qty so the sum exactly equals the original line discount.
- **`inventory_batches` is mostly append-only** (v2.8, ADR-2026-05-12-batch-immutability-rules). The `batch_immutable_fields` trigger blocks UPDATE to: `variant_id`, `batch_no`, `qty_received`, `cost_per_unit`, `manufactured_date`, `expiry_date`, `supplier_warranty_days`, `warranty_expires_at`, `received_at`, `purchase_item_id`, `supplier_id`. Allowed mutations: `qty_remaining`, `is_active`, `notes`. Audit 5 (`tgname = 'inventory_batches_immutable'`) verifies the trigger is attached — drop it by mistake and the audit catches it.
- **Toggle `products.has_batches` is guarded** (v2.8). Going false → true requires every variant's `stock = 0` (no orphan inventory). Going true → false requires no active batches anywhere on the product. The frontend `useUpdateProduct` checks both directions and raises `cannot_enable_batches_with_stock` / `cannot_disable_batches_with_active_batches`. Going forward, v2.9 will add `has_serials` and the two flags will be mutually exclusive at the application layer (per ADR-2026-05-12-batches-vs-serials-mutually-exclusive).
- **`deactivate_batch` directly decrements `variant.stock`** (v2.8, ADR-2026-05-12-batch-deactivation-temporary-pattern). Temporary pattern — v2.10 will introduce `inventory_adjustments` and rewrite this RPC to insert into the adjustments ledger. Until then, audit 1 (`variant.stock = Σ active batch.qty_remaining` for batched products) verifies the invariant after every write-off.
- **Two batch-visibility views cover the lifecycle** (v2.8 + v2.8.3). `batches_expiring_soon` is the preventative surface (`expiry_date - today <= alert_window AND expiry_date >= today`). `batches_already_expired` is the corrective surface (`expiry_date < today AND qty_remaining > 0`). Mutually exclusive by construction. The day a batch's expiry date crosses, it moves from one view to the other automatically; the dashboard's two widgets pick it up. Add other expiry-related views with care so they don't overlap these.
- **`product_with_default_variant.has_null_price_variant`** (v2.8.3) is an `exists()` aggregate over active variants where `price IS NULL`. It drives the catalog list's "Set price ⚠" surfacing + the `?needs_pricing=1` filter chip via `search_products(p_needs_pricing=true)`. When adding new columns to that view, preserve this aggregate or v2.8.3's catalog UX silently regresses.
- **Bulk write-off is a frontend loop over `record_partial_writeoff`, not a server RPC** (v2.8.3). `BulkWriteOffDialog` iterates the per-batch RPC with the same reason. Each batch gets its own write-off note in `batch.notes`. Don't combine into a single ledger row — the per-batch granularity is the audit trail v2.10's `inventory_adjustments` table will inherit.
- **Empty batches auto-deactivate** (v2.8.2). The `batch_auto_deactivate_when_empty` trigger fires BEFORE UPDATE on `inventory_batches` and flips `is_active = false` the instant `qty_remaining` transitions from > 0 to 0. Fires once on the transition — doesn't re-fire on subsequent updates to an already-empty batch (e.g. notes-only edits). Covers every code path that touches qty: FEFO decrement in `record_sale`, partial write-off via `record_partial_writeoff`, full write-off via `deactivate_batch` (whose explicit `is_active = false` write is now a no-op). New invariant: no batch can have `qty_remaining = 0 AND is_active = true`. Trigger order on `inventory_batches`: auto-deactivate → immutability → touch (Postgres BEFORE row triggers fire in name order; `is_active` is in the immutability trigger's allowed-mutations list so no conflict).
- **Partial write-off path** (v2.8.2). The "Write off batch" dialog accepts a `qty` (defaults to `qty_remaining`). User can drop it for partial RTV / damage scenarios. Always calls `record_partial_writeoff(batch_id, qty, reason)` — the auto-deactivate trigger handles the full-batch case when qty equals qty_remaining. RPC decrements `variant.stock` and `batch.qty_remaining` by exactly `qty` and appends a dated note like `2026-05-12 — Wrote off 2 unit(s): RTV to supplier`. v2.10 will swap the direct `variant.stock` decrement for an `inventory_adjustments` ledger entry; RPC surface stays the same.
- **Pricing and stock are catalog-decoupled** (v2.8.1). Product create form ONLY captures catalog data (name / variants / category / description / optional selling price / has_batches flag). Cost-of-goods + initial inventory flow exclusively through stock-in. Both `create_product_with_opening_stock` and `create_product_with_variants` accept null price and zero opening-stock as the new default. Batched products MUST go through stock-in for their initial batch — `cannot_seed_opening_stock_for_batched_product` raises if `has_batches=true AND opening_stock>0`. The "This is opening stock" checkbox on NewPurchasePage flips `purchases.is_opening` (audit-only flag; record_purchase math is unchanged). Null-price variants are hidden from POS via the existing 0-stock filter + record_sale's `variant_not_sellable` guard.
- **`suggest_batch_no(variant_id, received_at)` returns `<SHOPSP>-<PROD>-<YYMMDD>-<NNN>`** (v2.8). The shop prefix reads from `shops.shop_name` (not `shops.name` — there isn't one). Frontend uses this only for the stock-in batch_no pre-fill; the user can override before submitting.
- **Expired-sale policy resolves via `coalesce(products.expired_sale_policy, shops.default_expired_sale_policy, 'warn')`** (v2.8.4, ADR-2026-05-13-warn-as-default-policy). Null on the product means "use shop default" — don't backfill `'warn'` per product; the coalesce handles it and tightening the shop default retroactively works as expected. Both `record_sale` and `preflight_expired_sale_check` use the same resolution.
- **`record_sale`'s `p_confirm_expired_sale` parameter is only meaningful in `warn` mode** (v2.8.4). In `block` mode the policy is non-negotiable (the flag is ignored); in `allow` mode it's a no-op (FEFO walks the unfiltered candidate list either way). The flag is the explicit "cashier said yes" signal that the warn dialog produces.
- **FEFO with policy ≠ `allow` is a two-pass walk** (v2.8.4, ADR-2026-05-13-expired-sale-policy-three-modes). Pass 1 over non-expired batches (filter `expiry_date IS NULL OR expiry_date >= current_date`, order ASC by expiry — soonest-to-expire first); each chunk's `sold_expired = false`. If `v_remaining_qty > 0` after Pass 1, branch on policy: `block` raises `insufficient_non_expired_stock`; `warn` without confirmation raises `expired_stock_needs_confirmation`; `warn` with confirmation runs Pass 2 over expired batches ordered `expiry_date DESC` (least-expired-first per spec §3.2 — the just-expired stock leaves before the long-expired) with `sold_expired = true` on each chunk. `allow` is a single pass over the unfiltered candidate list with `sold_expired = (batch.expiry_date IS NOT NULL AND batch.expiry_date < current_date)` per chunk.
- **`sale_items.sold_expired` is a snapshot at sale time, not derived on read** (v2.8.4, ADR-2026-05-13-sold-expired-flag-snapshotted-not-derived). Set in `record_sale` per allocated chunk by comparing `batch.expiry_date < current_date`; immutable thereafter via the blanket `sale_items_no_modify` trigger. The receipt disclaimer, sale-detail badge, dashboard widget, and audit list all read the column directly — none of them recompute. Historical truth survives later writes to the batch (including write-offs).
- **`preflight_expired_sale_check` gates on `products.has_batches = true`** (v2.8.4, ADR-2026-05-13-preflight-rpc-for-expired-stock-check). Non-batched items always return `would_draw_expired = false` regardless of policy — the spec's naive pseudo-code would have flagged them true (zero batches in `inventory_batches`). When `would_draw_expired = false`, `expired_batch_ids` returns `'{}'`, never null, so the client never needs to null-check the array. The preflight is a UX optimization only; `record_sale` is the authoritative gate.
- **Receipt disclaimer renders only when BOTH conditions are true** (v2.8.4, ADR-2026-05-13-receipt-disclaimer-opt-in): `shops.expired_sale_receipt_disclaimer = true` AND the sale has at least one `sold_expired = true` line. POSPage computes the latter with a count query on `sale_items` after `record_sale` returns; the Receipt component takes a single `showExpiredDisclaimer` boolean prop. Disclaimer text is i18n key `sales:detail.receipt_disclaimer_default` (en + ur).
- **POS cart lines carry a `resolved_variant_id` next to `variant_id`** (v2.8.5). `variant_id` stays null for single-variant lines (server resolves at record_sale time); `resolved_variant_id` is the actual default variant id captured at add-to-cart from `ProductSearchRow.default_variant_id`. The batch picker needs it to query `inventory_batches`. Two fields, two purposes — don't conflate.
- **`search_products` returns `has_batches` + `default_variant_id`** (v2.8.5). The view `product_with_default_variant` and the RPC's RETURNS TABLE both had to grow. View change uses CREATE OR REPLACE with the new column appended at the end of the column list — Postgres rejects mid-list insertions in a view rebuild with "cannot change name of view column". Function rebuild needs DROP + CREATE because the RETURNS TABLE shape changed.
- **The batch picker doesn't gate selection on policy** (v2.8.5, ADR-2026-05-13-pos-batch-picker-ships-as-v285-polish). Even with `policy = block`, the cashier can pick an expired batch in the picker. The block/warn enforcement happens at submit time via `preflight_expired_sale_check` + `record_sale`, which see the picked `batch_id` and run the manual-override branch. Hiding rows in the picker would silently constrain the cashier without explanation.
- **When `cart.batch_id` is set, the preflight runs the manual-override branch** (v2.8.5). Preflight checks the *specific* batch's `expiry_date`, not the FEFO non-expired sum. So a cart line with `batch_id = <fresh-batch>` won't trigger the warn dialog even if other expired batches exist for that variant. Conversely, picking an expired batch on a single-variant line where there's plenty of fresh stock *will* trigger it. The picker's UX reflects this by surfacing the EXPIRED badge inline; the submit-time dialog is the safety net.
- **No user-facing "FEFO"** (v2.8.5). Shop owners don't speak inventory-jargon. Every UI string that referred to FEFO / "oldest" is now "auto-pick" (en) / "خودکار انتخاب" (ur). Keys touched: `pos:cart.batch_oldest`, `pos:cart.reset_to_fefo`, `batches:indicators.oldest`, `batches:indicators.reset_to_fefo`. New keys: `pos:cart.batch_next_up` ("Will be used"), `pos:cart.batch_auto_hint` (explanation banner), and the same pair on `batches:indicators.next_up` / `batches:indicators.auto_hint`. Code-side variable + comment usage of "FEFO" is kept (it's still the SQL algorithm name); only the visible strings changed.
- **Auto-pick suggestion is purely visual** (v2.8.5). When `currentBatchId === null`, `PosBatchPicker` computes `autoPickBatchId` client-side (first batch with `qty_remaining ≥ requiredQty`; prefers non-expired) and decorates that row with a brand "Will be used" badge + brand border. It does NOT pre-select the row; the cart's `batch_id` stays null and the server-side auto-pick still runs at submit. If a future change auto-applies the suggestion on render, double-check it doesn't trigger an unwanted dispatch loop — the picker is open ↔ closed many times in a single QA session.
- **`useRecordSale` / `useRecordPurchase` must invalidate `['product']`, `['batches']`, `['alerts']`** (v2.8.5). Without them, the POS batch picker showed stale `qty_remaining` on the next add-to-cart cycle, the product-detail page kept the old stock, and the dashboard alert widgets lagged a sale behind. The `['products']` (plural) key only covers the catalog list — `useProduct(id)` keys by `['product', id]` (singular) and the picker hook keys by `['batches', 'variant', variantId, 'active']`. Pattern: any RPC that mutates stock or batches should invalidate the same trio — match `record_partial_writeoff`'s onSuccess shape.

## Frontend / UI

- **DataTable `cell` signature is `(row) → ReactNode` only** — no index parameter. Code that wrote `cell: (_p, idx) => idx + 1` rendered NaN (the v2.3 PurchaseDetail bug). Precompute serial numbers from the rows array (`new Map(rows.map((r,i) => [r.id, i+1]))`) and look up by id inside cell.
- **POS product list: all "add" affordances live in the rightmost (actions) column** (v2.3 §6.3.2/§6.3.3, revised). The primary `[+]` IconButton sits on top, pack quick-add chips (secondary variant) stack vertically below it. Scan-only products replace the `[+]` with a muted "Scan only" caption while still showing pack chips. `ProductTable` widens the actions column to 160 px when `loadBreakdownsForActions` is set so chip labels don't truncate.
- **POS cart lines are self-labeling cards** (v2.3 follow-up, replaces the column-headers approach). Each line is a `surface-base` card with `border-subtle` + `shadow-xs` + `radius-md`, sitting on a `surface-subtle` panel background. Layout per card: header strip with product name (wraps freely — never `noWrap`) on the left and line total + × removal on the right; hairline divider; controls strip with Qty stepper + Price input each preceded by an uppercase caption label. No column headers above the list — the inline captions handle that job. Same composition from 320 px to 1200 px; the controls strip flex-wraps if the panel narrows. Tabular-nums on totals and the price input keep numbers visually aligned even with proportional fonts.
- **Dark mode is token-only — never use raw color scales for foreground text** (v2.4). The `[data-theme="dark"]` block in `tokens.css` only flips semantic tokens; raw scales (`--brand-700`, `--warning-700`, `--neutral-200`, etc.) stay constant. Components that hard-code raw scales for *visible* color (text, icon, leading bar) become hard to read on near-black surfaces. The semantic tokens to reach for are: `--text-brand` (replaces `--brand-700` for any "brand-colored" text/icon), `--status-{success,warning,error,info}-text` (replaces `--{success,warning,error,info}-700`), `--surface-inverse` / `--text-inverse` (for tooltips and inverse contexts), `--surface-muted` (replaces `--neutral-200` for subtle fills). Background fills with raw scales are usually fine because they're not load-bearing; foreground text is what fails legibility.
- **POS drawer must never mount/unmount the cart** (v2.5, ADR-0020). The POS product detail drawer is a *presentational* overlay over the POS page; cart state lives in `POSPage`'s `useReducer` and is independent of the drawer. The drawer's "+ Add to cart" footer calls a parent handler with the product id — it never owns the cart. Any future change that ties cart state to the drawer is a regression.
- **Stop propagation inside `renderActions` if the row is also clickable** (v2.5). `DataTable` cells don't stopPropagation by default — when a row has `onRowClick`, every click inside a cell bubbles up. POS wraps the actions Stack with `onClick={e => e.stopPropagation()}` so the [+] button and pack chips don't also open the detail drawer.
- **POS multi-variant rows show "Pick variant" instead of [+]** (v2.7, ADR-0029). `search_products` returns `has_variants` + `min_price` / `max_price` so the UI branches without an extra fetch. Cart lines are keyed by `variant_id ?? product_id` (the `lineKey` helper) — two variants of one product are distinct cart lines.
- **The v2.7 stock-in matrix is the expanding-line fallback, not the 2D grid** (ADR-0028). When a multi-variant product is picked on a stock-in line, a variant `<Select>` appears. Receiving N variants of one product = N stock-in lines. The full matrix UX (per-cell grid, per-cell pricing toggle, inline `+ Add Color value`) is on the open-todo list.

## RBAC (v2.9+)

- **Owner has every permission via implicit shortcut** (v2.9, ADR `2026-05-13-rbac-owner-implicit-shortcut`). The owner is identified by `user_shop_access.is_owner = true`. `user_has_permission(shop_id, key)` short-circuits to TRUE before consulting `user_shop_permissions` rows. **Owners NEVER have rows in `user_shop_permissions`.** Audit query AQ-19 verifies this — any owner with permission rows is a bug. Do NOT backfill rows for owners when a new permission ships; the shortcut covers them automatically.
- **The `_v28` wrapper-and-rename pattern is NOT dead code** (v2.9, migration 0076). Every v2.8.5 RPC was renamed `<name>_v28` and a new wrapper with the same external signature was created at `<name>`. The wrapper does AUTH check + permission check + delegation to `_v28`. The inner `_v28` body is the unchanged v2.8.5 SQL — kept intact for auditability. `EXECUTE` is revoked from authenticated on every `_v28`; only the wrappers are reachable by clients. **Future-Claude reading the codebase will see two function families and the temptation will be to "clean up" by inlining bodies. Don't, until v2.9.x has settled.** The inner bodies still call `current_shop_id()` (now permanently aliased to `current_active_shop_id()` per migration 0078 — safe because the legacy policies that depended on the v2.8.5 body were dropped in 0077). When you DO eventually inline (planned for v2.9.x cleanup), document the migration explicitly and verify no caller is left referencing `<name>_v28`.
- **The `app-shop-id` HTTP header is the active-shop transport** (v2.9, ADR `2026-05-13-rbac-set-active-shop-fallback-path`). The Supabase JS client must inject the header from `localStorage.nizaamify.active_shop_id` via a `customFetch` wrapper. The `current_active_shop_id()` SQL helper reads `current_setting('request.headers', true)::jsonb ->> 'app-shop-id'` per call, validates membership via `user_has_shop_access`, and falls back to "user's single shop" if the user has exactly one. **NO Supabase Pre-request hook is configured** — the per-call read is the v2.9 path on the project's Free tier. ~1ms per call; functionally equivalent. Upgrade to hook-based in v2.10+ if call-count cost ever matters.
- **Cost-bearing views project conditionally via materialized CTE** (v2.9, ADR `2026-05-13-rbac-permission-conditional-view-projection`). Each cost-bearing `_view` (products_view, product_variants_view, sale_items_view, invoices_view, customers_view, ...) is `security_invoker = false` with `with caller_perms as materialized (...)` at the top — one `user_has_permission(...)` call per query, not per row. Sensitive columns are projected as `case when cp.can_see_X then col end` against the materialized flag. **Adding new sensitive columns to these views**: put the column in the SELECT list wrapped in the case-when, NOT as a raw reference. The advisor lint `security_definer_view` fires 14 times for these views — accepted per ADR `2026-05-13-rbac-definer-safe-views`.
- **Search/list RPCs project conditionally in the wrapper, not the inner** (v2.9, ADR `2026-05-13-rbac-search-rpcs-conditional-projection`). `search_products`, `recent_purchase_products`, `list_customers`, `recent_customers` wrappers do `return query select id, name, ..., case when can_see_cost then avg_cost end, ... from <name>_v28(args)`. The inner `_v28` returns all columns; the wrapper NULLs sensitive ones. Don't add cost columns to the inner without also wrapping them in the outer.
- **Permission grants enforce dependencies at BOTH grant and revoke time** (v2.9, ADR `2026-05-13-rbac-dependency-rules-grant-time`). Catalog row `requires text[]` lists prerequisite keys. `modify_user_permission` raises `permission_dependency_missing` on grant if a required permission isn't granted; raises `cannot_revoke_required_permission` on revoke if a permission that depends on this one is still granted. **Owners must revoke in cascade order**: e.g., to revoke `view_customer_outstanding`, first revoke `receive_payment` (which depends on it). The runtime `user_has_permission` does NOT traverse the dep graph — it's single-key. Deps are a state-coherence guarantee, not runtime resolution.
- **Audit `_by_user_id` writes happen in the wrapper post-delegation, not the inner** (v2.9, migration 0080). After delegating to `_v28`, each wrapper UPDATEs the affected row(s) to set `created_by_user_id` / `updated_by_user_id` / `last_modified_by_user_id` from `auth.uid()`. Idempotent via `where ... and created_by_user_id is null` guards. The `_v28` bodies remain v2.8.5-shaped; the audit writes are a layer on top.
- **The `current_active_shop_id` and `set_active_shop` failure modes are explicit raises** (v2.9). Header missing → fallback to single-shop OR NULL → `no_shop_for_user` raise at RPC entry. Header is invalid UUID → `invalid_app_shop_id_header`. Header references a shop the user doesn't belong to → `no_access_to_shop`. Client error-mapping should distinguish these so the UI can prompt "Select a shop" vs "Re-authenticate."
- **`receive_payment` non-owner daily cap uses `pg_advisory_xact_lock`** (v2.9, ADR `2026-05-13-rbac-receive-payment-cap-applies-to-all-non-owners`). The wrapper acquires a transaction-scoped advisory lock on hash(shop_id, user_id, current_date) before checking today's total, so two concurrent under-cap calls cannot both pass the check and together exceed. Owner bypasses the lock + cap entirely.
- **Discount-cap enforcement applies BOTH explicit and implicit forms** (v2.9, ADR `2026-05-13-rbac-record-sale-permission-enhancements`). `record_sale` checks (a) explicit `line_discount_value` + `sale_discount_value` per-line and per-invoice; (b) implicit discount via `1 - (price_at_sale / variant.price)` when variant.price > 0. Same cap applies to both forms — a salesperson can't bypass a 5% cap by ringing up at `price_at_sale = 0`.
- **Profile team-read is OWNER-only despite design discussions implying manager+** (v2.9 cleanup, ADR `2026-05-13-v29-cleanup-permissive-policies` / ADR #23). The consolidated `profiles_self_or_owner_team_read` policy admits `(id = auth.uid()) OR (caller is OWNER of a shop where target is a member)`. Managers and salespeople with `view_team` permission still only see their own profile row at the RLS layer — team-page details for non-owners must be served via a DEFINER RPC (e.g. `get_team_for_active_shop`) that projects only the columns the caller's `manage_team_permissions` permission allows. **Do not** widen this RLS policy to manager+ without updating the ADR; the narrower scope was a deliberate choice during 0075 and preserved verbatim in 0081.
- **The audit query suite (AQ-01..AQ-23) is run by hand, not by cron** (v2.9, ADR `2026-05-13-v29-cleanup-permissive-policies`). The 23 queries live in `design/2026-05-13-rbac-attack-surface.md` §C.3 and the implementation plan calls for a "daily run during stabilization" — but there is no scheduled job that fires them. Today's path: copy §C.3 SQL → run via `mcp__supabase__execute_sql` → confirm all return 0. When v2.9.1 frontend lands and stabilization resumes, the manual cadence resumes too. **Automation is a v2.10+ ticket**: pg_cron + a Supabase Edge Function posting non-zero results to a Slack/email channel, or a GitHub Action running the suite on schedule. AQ-23 inherits this manual-run gap from the original 22 — adding it to the suite does not change the trigger model.
- **v2.9 frontend has no customer-delete capability** (v2.9.0.1 sweep, ADR `2026-05-12-v2-9-0-1-frontend-sweep`). Direct `customers.delete()` was removed in the v2.9 sweep because the v2.9 RLS state has no DELETE policy on `customers` and no `deactivate_customer` / `delete_customer` RPC exists. Replacement is deferred to the v2.10 customer-management ticket where soft-delete vs hard-delete vs khata-impact vs reactivation can be decided alongside returns/refunds/warranty work. The `CustomersListPage` "Actions" column shows view + edit only; the `useDeleteCustomer` hook is gone. **Do not** add back direct `customers.delete()` calls under v2.9 — they will throw `42501` and the design hasn't been resolved.
- **Backend RPC migrations that remove RLS policies on write-target tables MUST ship with the matching frontend call-site sweep in the SAME ticket** (v2.9.0.1 lesson, ADR `2026-05-12-v2-9-0-1-frontend-sweep`). v2.9 removed direct write permissions on `customers` (no INSERT/DELETE policy) and `shops` (no UPDATE policy) but the frontend still issued direct `.insert()` / `.update()` / `.delete()` against those tables. The synthetic test in 0076b ran under `set_config('request.jwt.claims', ...)` inside a transaction — which doesn't `SET ROLE` and skips the planner path real authenticated clients use. Four regressions surfaced the day a real owner logged in: RLS recursion, GROUP BY error in `current_active_shop_id` fallback, `42501` on customer INSERT, `42501` on shops UPDATE. **Going forward**: any migration that drops or tightens a write-target RLS policy must include the corresponding frontend hook migration in the same PR. Pair them; don't sequence them.
- **Append-only tables require audit columns written INLINE at INSERT, never via post-delegation UPDATE** (migration 0086, credit-sale P0001 regression). v2.9 migration 0080 installed the pattern "wrapper delegates to `_v28` body, then UPDATEs the affected row to stamp `created_by_user_id = auth.uid()`." That works for tables like `customers` / `products` / `inventory_batches` (the latter has an allowlist trigger). It does **not** work for append-only tables — `ledger_entries`, `invoices`, `sale_items`, `purchases`, `purchase_items`, `purchase_overhead_items` — whose immutability triggers (`*_no_modify`) block every UPDATE by design and cannot distinguish an "audit UPDATE" from a tampering UPDATE. Symptom: credit sale, payment receipt, or ledger reversal raises `P0001 / ledger_entries are append-only — reverse the entry instead of updating it`. Fix pattern (applied to `record_sale_v28`, `receive_payment_v28`, `reverse_ledger_entry_v28` in 0086): move `created_by_user_id` into the INSERT statement inside the `_v28` body using `v_user_id := auth.uid()`. Remove the post-delegation UPDATE from the outer wrapper. **Rule**: any future wrapper that touches an append-only table must write audit columns inline at INSERT inside the `_v28` body. Confirm by grep: `update public.<append_only_table>` should not appear in any v2.9+ wrapper body except for the columns explicitly allowlisted by the immutability trigger (`inventory_batches.qty_remaining` / `is_active` / `notes` / `last_modified_by_user_id`).

## RBAC frontend (v2.9.1+)

- **Frontend error dispatch matches on message text, not SQLSTATE** (v2.9.1, ADR `2026-05-13-v291-error-dispatch-message-text`). Every controlled raise in the v2.9 server defaults to `P0001` because the 31 `_v28` inner bodies have ~144 `raise exception '<key>'` lines without `using errcode = ...`. The outer wrappers all set errcode but raise propagates through unmodified. Touching `_v28` bodies is forbidden by the wrap-and-rename rule, so the 144 inner raises stay P0001. Frontend dispatches on `err.message` via `src/lib/errorMap.ts` (a `Record<string, string>` of 144 entries mapping server raise → i18n key). When adding a new RPC: add the corresponding error string to the map; the ESLint discipline rule (Phase F item) enforces routing through `mapErrorToI18nKey()` in catch handlers. **Revisability:** if maintenance burden grows in v2.9.2+, the alternative (adding `using errcode = '<distinct_code>'` to inner-body raises) remains available as a one-time migration — but only after re-examining the wrap-and-rename rule.
- **Synthetic Postgres tests use real session JWTs, never `set_config('request.jwt.claims', ...)`** (v2.9.0.1 lesson, [[feedback-synthetic-tests-real-role]] memory rule). The 0076b synthetic test used the `set_config` shortcut and missed four regressions that surfaced under real authenticated traffic (42P17 recursion, 42803 grouping, 42501 INSERTs). The shortcut doesn't `SET ROLE` and skips the planner path real PostgREST traffic uses. v2.9.1 inherits the rule: any synthetic SQL test must run via Supabase Studio SQL Editor while signed in OR via the application frontend with the real customFetch + JWT path. The MCP `execute_sql` tool runs as service_role and cannot satisfy this — its only role is data-integrity checks (AQ suite + invariants) that don't need `auth.uid()`. Test bed at `audit/2026-05-13-v291-phase-e-owner-synthetic-test.sql` documents the runner contract.
- **Audit gaps block pilot flag flips, even when they look like polish** (v2.9.1 lesson, [[feedback-audit-gaps-block-flag-flip]] memory rule). The Phase D cluster 6 `useUpdateProduct` deferral was initially framed as "v2.9.2 polish" — but under owner-only traffic (pre-flag-flip), the audit gap is invisible (owner has no `user_shop_permissions` row to compare against); the moment a non-owner edits anything, `_by_user_id` columns stay NULL forever (append-only triggers prevent backfill). The fix landed as migration 0089 + frontend hook migration before any pilot flag flipped. **Rule generalisation**: for any future RBAC-style rollout, before flipping a feature flag at a pilot shop, audit the direct-write hook list. Each hook reachable by non-owner permission grants must route through a `_by_user_id`-writing wrapper RPC. The Phase F readiness checklist in `tasks.md` task #10 is the authoritative gate.
- **`update_product` does NOT change `is_active`; route to `archive_product` instead** (v2.9.1 task #23, ADR `2026-05-13-v291-mig-0089-update-product-extension`). Archive vs edit semantics are intentionally separated. `update_product` handles name, description, category_id, default-variant price (single-variant only), is_scan_only, has_batches (with server-side guard rails), expiry/warranty alert days, and expired_sale_policy override. `archive_product(p_id, p_is_active)` handles is_active toggle AND cascades to all variants. Callers that touch is_active in the same submit (e.g. `ProductEditDialog`) detect the change and call `useArchiveProduct.mutateAsync()` after the `update_product` call — only when is_active actually changed, to preserve the archive_product permission gate for edit-only users.
- **`/invite/accept/:invitation_id` is a code-entry page only — invitee signs up at `/signup` FIRST** (v2.9.1 cluster 4, ADR `2026-05-13-v291-invite-accept-deferred-features`). The PRD B.4 mockup showed password fields; the reality requires Supabase admin API for programmatic password-set (server-side service_role only). v2.9.1 ships the two-step flow: invitee receives the URL + 4-digit code verbally from the owner, signs up at `/signup` with the invited email, verifies, logs in, then visits the accept URL and enters the code. On successful accept, the page self-updates `profiles.onboarding_completed = true` (`profiles_self_update` policy admits it) so the invitee bypasses the owner onboarding wizard. The one-page signup+accept UX is a v2.10 candidate (needs an Edge Function with service_role + email verification skip).
- **Column-level REVOKE is a no-op when a table-level GRANT SELECT is in place** (v2.10a, migs 0092 + 0093, ADR `2026-05-13-v210a-definerize-financials-and-column-revoke`). PostgreSQL semantics: when `GRANT SELECT ON public.foo TO authenticated;` exists, a subsequent `REVOKE SELECT (col) ON public.foo FROM authenticated;` is silently ignored. The verified-the-hard-way pattern: drop the table-level grant entirely, then `GRANT SELECT (col1, col2, ...) ON public.foo TO authenticated;` with the explicit safe-column list — omitted columns are blocked. Mig 0093 applied this to `public.sale_items` to close the `cost_at_sale` raw-API leak from mig 0091. **Maintenance contract**: any future migration that adds a column to a table using this pattern MUST also `grant select (<new_col>) on public.<table> to authenticated;` or the column is invisible to every application read. Mig 0093 header documents the current `sale_items` baseline; cross-check that file when adding a new column.
- **Cost-bearing reads must route through DEFINER views, not raw `from('sale_items')`** (v2.10a, mig 0092). After mig 0093, `authenticated` cannot SELECT `sale_items.cost_at_sale` from the raw table — every direct nested-select that includes the column errors with `42501 permission denied for table sale_items`. Read cost values via `sale_item_financials` instead (now `security_invoker = false`, row-filtered on `view_all_sales OR cashier_id = auth.uid()`, conditionally projects `cost_at_sale` / `line_cost` / `line_profit` on `view_sale_cost`). `useSale` (`src/features/sales/hooks.ts`) was refactored to drop `cost_at_sale` from the nested `sale_items(...)` PostgREST select and reads it from `sale_item_financials.cost_at_sale` instead. **Pattern for new cost reads**: never write `.from('sale_items').select('..., cost_at_sale')`. Use `.from('sale_item_financials')` or `.from('sale_items_view')` (v2.9 conditional projection view).
- **`RBAC_TEAM_UI_ENABLED` env flag gates `/settings/team` + the sidebar entry** (v2.9.1 B.9, ADR `2026-05-13-v291-b9-feature-flag-per-shop-manual`). Default OFF. Pilot deploys set `VITE_RBAC_TEAM_UI_ENABLED=true` in their `.env.local` (or env-specific config). The flag is checked in `src/lib/featureFlags.ts` and consumed by both the route guard (which short-circuits to `/dashboard`) and the sidebar config (which omits the entry). Per-shop manual flip via env-edit + redeploy; remove the flag entirely after the first 1-2 pilot shops are stable for 30 days.
- **Permission cache has a bounded 60s stale window** (v2.9, ADR `2026-05-13-rbac-client-cache-staleness-bounded`; v2.9.1 wires the snackbar UX). `useSelfPermissions()` queries `get_user_permissions(auth.uid())` with `staleTime: 60_000` + `refetchOnWindowFocus: true`. When an owner revokes a permission, the affected staff member sees stale UI for up to 60s. Per B.6, the team-page revoke flow surfaces a success snackbar with "Affected staff may see stale UI for up to 60 seconds" so the owner sets the right expectation. Realtime subscription is a v2.10+ candidate; the 60s bound is intentional.
- **AQ-23 exempt list is the source of truth for "shop-membership-neutral" wrappers** (v2.9 ADR-23 + v2.9.1 extensions). The exempt list at `design/2026-05-13-rbac-attack-surface.md` §C.3 grew from 11 (v2.9 baseline) to 13 (v2.9.1 migration 0087: `get_active_shop`, `get_shop_settings`) to 14 (v2.9.1 migration 0088: `get_invitation_for_acceptance` — pre-shop helper, invitee has no shop access at call time). When adding a new DEFINER wrapper that legitimately doesn't fit P1/P2/P3, update the exempt list in `design/2026-05-13-rbac-attack-surface.md` §C.3, the test bed at `audit/2026-05-13-v291-phase-e-owner-synthetic-test.sql`, and document the rationale in an ADR. Never silently widen.
- **AQ-24 catches legacy `current_shop_id()` callers in new SQL** (v2.9.1 ADR `2026-05-13-v291-aq24-baseline-allowlist`). Migration 0078 created a permanent alias `current_shop_id()` → `current_active_shop_id()` to keep pre-v2.9 callers working. v2.9.1+ code must call `current_active_shop_id()` directly. AQ-24 allowlists the 38 `_v28` inner functions (preserved per the wrap-and-rename rule) and 2 pre-v2.9 views (`daily_sales_7`, `expenses_by_category_mtd` — v2.10 cleanup target). Any new SQL object outside the allowlist that references `current_shop_id()` is a discipline violation surfaced by the audit.
